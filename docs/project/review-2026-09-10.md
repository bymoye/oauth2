## Authorization-code replay and recovery

A consumed marker contains redemption binding facts, the access-token JTI and
expiry, and the optional refresh-family identity. Its retention is the access
token lifetime when no refresh token was issued, or the initial refresh-token
lifetime otherwise. A matching replay can use those identities to revoke the
issued credentials. An expired or evicted marker produces a missing-code
rejection; it cannot turn into a pending authorization code.

Refresh rotation can extend successor lifetimes. The initial consumed marker
therefore does **not** promise replay detection for the lifetime of a family
that is continually extended. That boundary must not be described as an
unlimited retention guarantee, nor removed by silently reducing the TTL.

The cross-store hypothesis in the review assumes PostgreSQL retains a
completed issuance while Valkey restores the old pending code **in the same
state epoch**. Such an inconsistent restore is outside the supported recovery
procedure. Transient keys include the deployment, state epoch and tenant;
recovery changes the epoch, invalidates durable refresh authorization, waits
out access/ID-token validity plus skew, and keeps public ingress closed until
the process completes. See [HA operations](../operations/ha-operations.md),
[configuration](../operations/configuration.md), and
[update and recovery](../operations/one-click-update.md).

This is an operational invariant, not a claim that arbitrary manual rollback
is safe. No additional distributed-transaction mechanism or durable
authorization-code identity migration is introduced by this review.

## Scope of simplification

Token issuance and response delivery have separate boundaries. The public
token endpoint reloads and rejects inactive clients before grant dispatch.
The new owner-row locks order a fresh durable issuance commit against
deactivation. Recovery of an already persisted response creates no new
credentials; deactivation revokes its recorded access-token identifiers and
refresh families. The transaction does not attempt to include network response
delivery or add a second recovery transaction.

The existing separation of protocol policy, persistence, transport, and the
optional controller remains. Separate client authentication and token sender
binding protect different facts and remain separate. FAPI refresh policy and
the documented restricted JWT-bearer/token-exchange profiles remain intact.
Suggestions for a generic VCI transaction interface, broader protocol support,
or a new verifier cache are not established defects and are not implemented
as part of this correction.

Maintenance documentation is checked against the current manifests,
configuration allowlists, release contracts, scripts and workflows. Dated
test, certification and performance records remain historical evidence; their
index labels and links must not imply validation of a newer revision.

## Current-format cleanup

Before 0.5.0, releases do not preserve compatibility with historical versions.
The server now has one signing-key persistence path: the encrypted database
keyset. The file backend, file-to-database import, inactive path setting, and
performance keyset container are removed. Signing, rotation, external signers,
and request-object encryption remain on the database path. Historical SQL
migration records remain database lifecycle facts; they are not alternate
runtime format readers.

NazoAuthCtl removes schema-1 journal conversion, re-signing of stored requests,
unreachable old-data import options, and update-time mount/environment
conversion. Current recovery retains the original signed request. Unsupported
formats are rejected without rewriting the input. Host protocol is 11 and
recovery plan is 2.

The English and Chinese server READMEs and controller README are rewritten.
First installation now documents administrator creation, MFA enrollment,
controller binding, and verification in that order.
